## Technical design decisions

- **Plugin, pack, and tool hierarchy, with per-run pack instances.** A plugin is an entry point linked in as a crate or loaded as a DLL. It provides zero or more packs, and each pack provides zero or more tools. On load, a plugin announces its packs as text metadata only. When a prompt runs, the engine creates a pack instance for that run, and it lives for the whole run. Reason: a pack needs its own persistent state, such as a cache or a persistent connection, and three prompts running at once each get their own pack. State shared by all packs, such as a Tokio runtime or worker threads, goes in the plugin instance, so no tool spawns its own runtime. [Vinnie 19:06] [Vinnie 24:49-26:11]
- **Bashkit plugin.** Runvil now has a shell tool through a plugin wrapping Bashkit, a virtual bash shell with a virtual file system and 167 emulated, LLM-friendly command-line tools. The plugin lives in its own repo so it can be developed independently. Reasons: Runvil gets Bashkit's upstream improvements for free, and they don't "pollute the main build". [Vinnie 37:42-39:02] [Vinnie 40:41]
- **No file-writing API in the Bashkit plugin, on purpose.** Reason: Vinnie is not ready to let the harness write files on his computer. [Vinnie 41:53]
- **Markdown parsing in the engine.** `markdown.parse` returns a structured, nested table of blocks (a heading block with children, paragraph blocks, and so on), and every character of the text maps to some element. Reason: documents like Paperweight's papers can be chunked more cleanly, with a parse instead of "a big ugly lua". [Vinnie 44:01-44:52]
- **Prompt object and templates in Markdown fences.** The prompt object represents the prompt's Markdown. A template can live in a fenced block in a prompt section and be pulled out with something like `prompt.section(...)`. Reason: it replaces building templates in Lua by string concatenation (for example Kirill's Nash payoff-matrix template), so the template is one line and the Markdown stays readable. [Vinnie 45:33-47:16]
- **Run database (vision).** Every agent window or prompt run is tied to an SQL database that records every event, effect, input, and output, including intermediate files in the store. A developer tool will let a model open one run's database, or compare two, for example to decide which prompt gave better search results or extraction. Reason: comparing runs lets you iterate on prompts. [Vinnie 34:00-35:46]
- **Peel-back file view in Workshop (vision).** A small corner control (about an 8-pixel triangle) peels back to show a time-ordered log of a run's intermediate files. They open read-only in the editor as database blobs and can be dragged into the agent window as chips. Reason: "every little artifact becomes visible", to both the user and the model. [Vinnie 36:03-37:17]
- **Workshop supports multiple agents.** Workshop is not tied to the one chat agent, and other agent prompts can be added as options. Reason not stated. [Vinnie 6:44-7:30]
- **Contested principles in Vinnie's design scribe.** His design-profile version of the scribe sorts design principles as settled, open, or contested (two or more participants disagree). Reason: over each transcript, collect what is settled, see what is left, and let the humans resolve it. Andrew's classifier adds the case where one person disagrees with himself.
